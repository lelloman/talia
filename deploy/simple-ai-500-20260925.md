The delivered 19:00 Europe/Rome report
`report-b20c0d05d10cc97324baff36beeacc95` failed its optional analysis step.
All evidence below was read from the running services; no SimpleAI configuration

## Confirmed failure

SimpleAI audit request `14dd8213-dfe1-4d45-ab22-1334c3d4e9d3`, model `code:smart`,
started at 17:00:14.510 UTC and returned HTTP 500 after 120,083 ms. Its error was:

> Connection failed: Failed to wake inference runners: Timeout waiting for runner to connect after 120s

The deployed configuration has `gateway.wake_timeout_secs = 120`.
This was a runner wake/connection failure, before model loading or inference.
It was not Talìa's twenty-minute report deadline, malformed assessment JSON,
or an inference refusal. A passing `/health`/`simpleai_up` check did not test this
cold-start path.

## Correlated timeline (Europe/Rome, UTC+2)

- 19:00:14.575: idle-manager sent Wake-on-LAN for `strix-halo-01`.
- 19:02:14.601: SimpleAI returned HTTP 500 after its 120-second wait.
- 19:02:57.074: idle-manager logged wake timeout and retry, attempt 2.
- 19:02:57.109: it sent the second Wake-on-LAN packet.
- 19:03:34: Halo1's current kernel boot began, according to `uptime -s`.
- 19:03:45.662: SimpleAI registered `strix-halo-01` from Halo1.

Registration occurred about 211 seconds after the initial wake and 49 seconds
after the retry. Halo1's systemd startup report recorded 48.627 seconds including
34.655 seconds in firmware; the runner is the user's `simple-ai-runner.service`.
This is consistent with the second wake attempt booting the host normally.
The logs establish when packets were sent, not whether the first reached the NIC;
why the first attempt failed is not established.

Idle-manager source allows three wake attempts, each with a 120-second timeout,
checked by its polling loop. Its observed retry occurred after about 163 seconds.
SimpleAI's independent 120-second wait ended before that retry.

## Recommended correction

Align SimpleAI's bounded wake wait with idle-manager's retry/startup lifecycle,
within the overall report budget. Raising only Talìa's report timeout cannot help:
SimpleAI already returns a terminal 500. A warm success is not sufficient
verification; exercise a sleeping runner that requires a wake retry. Mapping a
wake timeout to an explicit service-unavailable result would also be clearer than
an undifferentiated 500. Improving packet delivery/retry timing is a separate
investigation from the confirmed timeout mismatch.
